企业知识库 MCP 工具（kb-tool）优化过程报告

日期：2026-09-11　|　项目位置：C:\Users\ASUS\Desktop\CQ-YWZX\kb-tool　|　宿主环境：WorkBuddy + LM Studio 本地模型

一、背景与目标

kb-tool 是一个部署在本地 venv 中的 RAG 检索服务（BGE 向量 + BM25 混合检索），以 stdio 方式接入 WorkBuddy，作为 enterprise-knowledge-base MCP 服务，供对话模型检索公司制度文档（考勤、休假、报销等）。

实际使用中反复出现同一失败模式：新会话首问"公司年假制度"，模型不调用知识库工具，而是搜本地文件或反问用户，导致回答错误并浪费 3~4 分钟。优化目标：在不牺牲便携性（拷贝项目 + 一条 MCP 配置即可在任意电脑使用）的前提下，让首问稳定命中。

二、问题清单与根因

问题①｜MCP 握手耗时 13.5 秒
原版 mcp_server.py 启动后在主线程串行加载 torch → faiss → scipy/sklearn → sentence_transformers，再加载 BGE 模型与索引，全部完成后才开始应答 MCP 协议握手。日志实测：doConnect OK, elapsed=10224ms（最长达 13.5s）。
问题②｜工具清单快照早于工具就绪
WorkBuddy 在首问发出的瞬间对可用工具拍快照发给模型；而 MCP 进程握手要 13.5 秒。11:35 会话日志实锤：提问发出于会话创建后 0.14 秒，此时服务状态为 connecting，被排除在快照外；SDK 会话日志全文检索 search_knowledge_base 零命中——工具从未进入模型视野。
问题③｜后台线程预热死锁（Windows Loader Lock）
第一版修复将预热挪到后台线程、让握手先行——父进程事件循环下，后台线程 import torch 直接卡死 120 秒。实测证明：本机环境下与 anyio 事件循环共存时，部分 C 扩展（torch、sklearn、sentence_transformers）禁止在非主线程首次加载。
问题④｜工具函数内延迟 import 同样死锁
改为握手先走、首次调用工具时再加载重库——FastMCP 将工具函数放在 worker 线程执行，同样触发死锁，调用 90 秒超时。结论：单进程内重库只能在主线程加载，此为硬约束。
问题⑤｜小模型工具选择错误
即使某轮工具已全部就绪（13:36 会话：MCP 1.16 秒连上、提问前索引完成），qwen3.5-9b 仍选择 Glob×6 + WebSearch 而从不调用 ToolSearch；gemma-4-e4b 也在规划 2 分 19 秒后选择 WebSearch。结构性原因：WorkBuddy 将 MCP 工具做成延迟工具，首轮请求里模型看不到 kb-tool 已写强的"【必须调用】"描述，只能看到泛化的 ToolSearch 入口。

尝试做法结果

评估弃用换更快 embedding 模型压缩加载13.5 秒大头是 torch/scipy/faiss 的 C 扩展导入，换模型仅省 1~2 秒，治标不治本

尝试 A/B 的失败共同证明了：必须把重库整个移出父进程——这正是最终方案的由来。

四、最终方案

方案一（已实施）｜子进程隔离，握手先行
· 父进程 mcp_server.py 只加载 MCP 协议框架即启动 stdio 服务，握手 0.6 秒；
· 检索引擎整体移入新增子进程 rag_worker.py，在子进程自己的主线程加载 torch/sklearn/BGE（绕开父进程死锁），预热约 6.3 秒，与用户打字时间并行；
· 父子进程以 JSON 行协议通信；含容错：子进程崩溃自动重启重试、读超时强杀回收、退出时优雅 shutdown，无孤儿进程；
· 检索内核（retriever/embeddings 等）一行未改；mcp.json 零改动，stdio 单配置便携性不变。
方案二（已实施）｜平台层"常驻路标"，修复模型选择问题
· ~/.workbuddy/MEMORY.md 写入常驻规则：公司制度类问题必须用 enterprise-knowledge-base 检索、禁止用 WebSearch 回答公司内部制度（每个新会话自动注入）；
· 新建用户级 Skill enterprise-kb-query：其名称与触发词（年假/考勤/报销/员工手册等）常驻每轮会话的技能清单，补偿延迟工具的不可见性。
方案三（已实施）｜对话模型升级（硬件验证后）
本机配置：Intel Core Ultra X7 358H / 32GB 内存 / Intel Arc B390。
· ~/.workbuddy/models.json 追加 qwen3.6-35b-a3b（MoE，3B 激活，实测 25.5 tok/s，工具调用正确、参数规范）与 qwen3.6-27b 两个条目；
· 实测对比后推荐 gemma-4-e4b（5.3GB，29.2 tok/s 全场最快，驻留时内存余 12.2GB，工具调用通过）——35B-A3B 虽能力更强但驻留后内存占用达 98%（仅余 0.4GB），存在把 kb-tool 挤入交换区的风险。

六、验证结果

验证项结果
MCP 握手耗时13.5s（原版）→ 6.8s（第一版）→ 0.58~0.62s（最终版）
检索正确性模拟真实 MCP 客户端调用 search_knowledge_base("公司年假制度")，正确返回《企业员工考勤与休假管理制度》年假条款（满1~5年5天/满5~10年10天/满10年15天，次年3月底前休完）

生命周期鲁棒性强杀全部子进程 → 下次检索自动重启成功（6.6s）；强杀父进程 → 子进程自行退出，无孤儿进程
模型能力35B-A3B 与 gemma-4-e4b 在带工具请求中均正确调用 search_knowledge_base 且参数规范（对比 9B 实战从不调用）

七、遗留事项与建议

  • 待用户真实验证：开新会话直接问"公司年假制度"，确认首问命中（当前会话内 MCP 进程仍是旧代码，无法自证）。
  • 备份清理：验证通过后，kb-tool 目录中的 mcp_server.py.bak、mcp_server.py.pre-subprocess.bak、config.py.bak 可删除。
  • 可选叠加优化（方案二 ONNX 轻量化）：用 onnxruntime + tokenizers 替换 torch + sentence_transformers 加载 BGE，把子进程冷启动 6.5s 压到约 2.5s；需转换模型并回归验证检索数值一致性。
  • 模型使用提示：若选 35B-A3B，建议 LM Studio 开启自动卸载（切换模型时释放内存），且避免同时驻留多个大模型。
  • 已知环境现象（与本改动无关）：本机启动器会为每个 python 进程复制一个同命令行的"孪生"进程，旧版部署同样存在，不影响功能。
